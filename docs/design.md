# 已确认设计

本文件记录已经确认的项目基础、玩法与世界观约束。模块组织见[基础架构方案](architecture.md)。具体内容数量、平衡数值和机制边界在对应模块实现前讨论，不继续逐项提前提问；已经确认的规则继续沿用。

## 项目基础

- 游戏中文名为《局部显现》，英文显示名为 **Local Manifestation**，统一使用单数与标题式大小写。主菜单、窗口标题按客户端语言显示对应名称。
- 定位为低收费买断制独立游戏，公开游戏本体、SDK、开发工具和文档源码。具体价格、开源许可证和发行渠道尚未确定。
- 开发者为项目发起人与协作助手，暂不考虑截止时间。
- 主体语言 Go；Windows 桌面客户端采用 Ebitengine，独立无界面服务端支持 Windows 和 Linux。
- 引擎和基础系统由 Go 实现，原版与模组的内容行为共同使用 JS，JSON 提供数据定义。
- 客户端、服务端、共享逻辑、SDK、工具和文档在一个主仓库维护。
- 先提供基础架构说明，再编码；原型使用几何图形和占位资源。
- 第一个可玩里程碑覆盖完整多层冒险循环。
- JSON 本地化系统默认提供简体中文和英文，允许客户端独立切换语言。
- 先本地及局域网开发，之后准备公网环境。最终必须有至少两台不同设备可连接的公开地址，并提供玩家无需开发者解释即可理解的游戏规则。

## 世界观与背景基调（2026-10-09）

- 基础设计元素包含洛夫克拉夫特、概念型敌人与大致世界观。Neta 元素由用户提出，现阶段不考虑。
- “冷静、诡异、日常、荒谬”仅作为背景基调，不直接推导其他设定、表现职责或玩法要求。此前将四者分别分配给界面、日常物件、异常和荒谬表达的建议已被用户否决，不作为后续依据。
- 时代为当代。正常社会存在于大约一半的地区，主要是大国和岛国；其余地区被同化，相关信息偶尔通过碎片信息展示。同化的来源、过程和具体规则未确定。
- 玩家身份为探索者；指引来自梦境，探索缘由也与梦境有关。梦境的来源、内容和约束尚未确定。
- 基地为个人据点；既有简约近代、基地与工作室式 UI 和大厅设计继续沿用，不据此推导额外世界观。
- 概念型敌人源于宇宙规律，玩家面对的是局部显现。越高层级越抽象；初期偏人类描述，后期偏概念描述。具体敌人与视觉表现尚未确定。
- 魔力实际为科技产物，只在探索领域使用。
- 现阶段不考虑主线剧情；世界观在物品描述等位置适当展示。正常地区公众对异常的了解程度，以及人类对魔力原理的理解程度，现阶段不重要，不展开设定。
- 整体角色与场景美术的具体表达方式待定。

## 联机与视角

- 合作闯关，共同挑战地图和 BOSS；不设置最低玩家人数，单人服务器可以正常开始。默认人数上限为 8，可通过特殊配置提高。
- 一个服务端进程只承载一个联机房间；同一冒险内可并行运行多个战斗场景。
- 服务端统一裁定。客户端发送操作意图，移动、命中、伤害、资源消耗和奖励结果由服务端处理。
- 通过地址和端口连接。客户端启动的服务器仍为独立进程，此时房主是管理员。
- 俯视和斜俯视可以切换，共用世界坐标和碰撞规则。
- 每个房间的场地为六边形，内部网格也为六边形网格。
- 逻辑刻与渲染帧独立：服务端以固定 30 或 60 次/秒推进逻辑，客户端绘制频率由独立帧率上限决定，不能通过降低逻辑频率限制 FPS。
- 网络快照频率作为独立参数。客户端在服务端快照之间平滑显示位置，显示插值不修改服务端裁定；伤害、冷却、状态持续时间等不依赖绘制帧数。
- 提供键盘与鼠标两种操作模式，均以指针方向攻击；详细输入绑定沿用已经讨论的规则。
- 战斗外不因缺少战斗场景而禁止攻击、闪避等常规行为；生命状态、控制效果、资源和冷却继续生效。

## 多层冒险

- 主流程为 5 层，后续为无限流程。5 层主流程此前已经决策，本次补齐记录；主流程与无限流程的衔接及结算细节在依赖模块实施前确认。
- 六边形战略地图由可通行路径连接，不是所有相邻节点都连通。每层以普通或强化 BOSS 的完成作为结束条件。
- 玩家在实际房间内移动并通过真实入口跨房；小/大地图仅查看，不能点击传送。采用独立房间模拟，连接区域也是完整六边形房间，以“通路”“野外”等命名，进入不消耗行动力。无房间区域用“悬崖”“山壁”等地形名表达，不生成可进入的房间。
- 跨入或离开战斗房间继续尚未出手攻击的剩余前摇，保留攻击冷却、闪避、无敌剩余与充能进度。已经发出的攻击/技能射弹可以跨房运行；房间切换不重置寿命、穿透或命中记录。射弹空间运行与伤害资格独立：未参与该房战斗的玩家不能伤害房内敌人，也不触发对应命中效果。
- 个人行动力为 X_f，队伍只有一个共享池 Y_f。X_f 与 Y_f 可以不同并随层变化；同层所有玩家个人初值一致，之后独立消耗。
- 层开始记录初始行动力。初值成长从下一层生效，当前层地图不因后来获得成长而重新生成。
- 个人节点由进入者分别付费；共享节点通过团队决策后支付一次开门费用。批准开门与本人是否进入是不同选择。
- 决策规则由房间配置，默认通过比例为 70%，开局前可设置。
- 不预留最后一点共享行动力。用最后一点进入普通 BOSS 时，仍是普通 BOSS。
- 共享行动力归零后出现进入强化 BOSS 的选项，剩余个人行动力仍可用于合法探索和救援；进入强化 BOSS 才推进对应集结和结算流程。
- 实际进入强化 BOSS 时，暂停且未完成的场景强制按未完成结算，保留已经获得的收益，不提供未完成部分的奖励。
- 强化 BOSS 引入本局团队诅咒，后续层个人初值与共享初值各减 1，诅咒不叠加；通过规定的内容解除。
- 战略地图、节点类型、商店类型及可通行关系按已确认的公开规则展示；提示采用模糊的一句话描述。

## UI 与玩家配置

- 战斗世界覆盖整个窗口，HUD 叠加其上；默认排列参考用户指定的泰拉瑞亚式 UI。
- 左上四技能，下方四消耗品；右上小地图，下方视角控制，再下方队友状态。同房间队友置顶并有特殊边框。
- 底部中央为生命和特殊资源条，上方状态栏；右下为当前武器、护甲、背包入口，背包打开普通窗口。点击小地图打开大地图。
- 个人和共享行动力在小地图内部左下角显示；闪避储存在血条右侧用圆点显示。
- 设置支持拖动各 UI 位置并保存到客户端配置；默认布局和自定义布局都不影响世界坐标或服务端裁定。详细边界见[HUD 与跨房移动](history/hud-navigation.md)。
- 语言切换和按键自定义作为设置子页，HUD 不再单独放语言按钮。绑定按输入模式编辑，提示从实际绑定派生。
- 按钮默认使用图标和已绑定快捷键；Hover 显示名称、说明及操作/禁用原因。状态图标默认只附持续时间和整体等级，各层来源、剩余时间和效果在 Hover 中展开；层实例仍无等级，护盾仍是无等级特殊状态。
- Hover 与普通窗口严格区分：Hover 跟随鼠标、只读、无关闭/确认/取消、不允许拖动或固定，唯一的详情交互是 Shift；普通窗口可拖动、关闭并同时打开多个。状态左键不打开额外页面，Hover 默认显示简单描述、层数和持续时间，Shift 再显示具体计算。

## 场景与成长

- 节点定义参与人数、收益、目标和中途加入规则。普通战斗可在波次间加入，特殊内容可提供快速支援；大多数其他节点禁止中途加入。
- 一个战斗场景内全部成员倒地时，暂停并保留未完成战斗；队友可按入场或支援规则进入，完成战斗后救援。
- 波次间仍属于战斗中，不能作为战斗外救援时点；整个队伍均倒地或死亡时判负。
- 倒地、救援、死亡、复活及惩罚系统互相独立表达。死亡保留当层未使用的个人行动力，复活时按同层余额或新层初始化规则恢复。
- 初始机体提供初始属性和装备差异，不强制职业。武器和技能形成近战承伤、远程物理持续输出、远程控制与爆发等倾向。
- 局内成长包括等级、饰品、武器更新和强化、主动技能、护甲；护甲有头部、身体、腿部和脚部。
- 同时装备并使用一把武器，背包可存放多把。标准模式为 12 个饰品槽，背包容量有限；游戏开始前的特殊设置可调整容量，饰品槽可以无上限地动态扩容。
- 枪械使用现实中的枪械名称与型号；具体型号及游戏内性能随内容设计确定，不以虚构功能名代替枪械名称。
- 不考虑套装奖励，装备收益由各件自身的属性与效果组合提供。
- 大部分掉落、经验和货币归玩家独立持有。可以交换物品，不直接交换货币。
- 新成员在层间准备加入，按当前层预设成长补偿；已在本层确认回归的成员可在临时掉线后重连。

## 敌人成长设计约束（2026-10-09）

- 当前敌人成长设计采用粗略推算，不以精确数值控制的方式确定成长曲线。
- 饰品分为三档：一档主要效果提供大约 10% 的增益，二档主要效果提供大约 20% 的增益，三档主要效果提供大约 30% 及以上的增益。参考明日方舟集成战略体系；上述百分比描述主要效果，不是整件饰品的最终战力增幅。
- 饰品的增益遵守已确认的同名乘区加算、不同名乘区乘算规则。玩家需要设法分散乘区以获得最大收益；不能将任意 12 件饰品直接视为 12 个独立乘区。
- 三档中的强条件、强配合特殊饰品允许产生远超 30%、甚至成倍的收益。
- 标准为12个饰品槽，0.7.0已同步运行默认。
- 每次战斗平均获得一个饰品，不改写为每次战斗保证恰好一个。
- 不考虑部分特殊三档饰品时，等级与武器本体合计、饰品对输出成长的贡献约各占 50%。用户确认可按两边提供相近倍率、再相乘来粗估；这是设计估算口径，不是新增实际伤害公式。
- “百倍、千倍甚至更高”仅为成长空间的抽象描述，不刻意追求，不设为某层必须达到的输出目标，不由此倒推固定成长曲线。
- 普通难度通关只需要最终综合战斗能力达到完整构筑的约四成；不是获得四成成长机会。综合战斗能力不是已定义的单一面板数值，不能直接把所有属性或最终输出统一乘 0.4。
- 极强构筑允许碾压普通房间，并迅速击败 BOSS。
- 多人带来的敌人增长结合数量与单体生命两方面。
- 具体敌人成长曲线、各属性增长关系与机制变化仍待讨论；本轮仅记录设计，不修改正式内容或开发数值。
- 第一轮敌人、饰品与装备已批准并接入，见[内容设计](content-batch-01.md)及[效果口径与实装记录](history/content-batch-01-stage.md)。9项效果边界由用户授权开发者决策。

## 伤害与状态

- 伤害计算及其结构化解释来自同一次求值，默认显示最终数值，按 Shift 等操作展开来源、乘区和计算过程。
- 计算模块可供实际结算、预览、装备比较和调试复用，独立于渲染、网络和 JS 运行时。
- 基础属性为力量、敏捷、体质、智力、感应、魔力；武器基础伤害可以由属性系数和固定值组成。
- 伤害类型包括物理、火焰、寒冷、电磁、化学和纯魔力伤害；护甲、类型抗性、百分比减伤及护盾按既定规则处理。
- 护甲提供固定值减伤，部分伤害类型可忽略护甲。百分比减伤在固定减伤后计算，各项分别相乘；最低伤害为 1，免疫等特殊规则另行处理。
- 同名乘区内加算，不同乘区相乘；普通加算、乘区乘算、最终加算与暴击的顺序沿用已确认规则。
- 默认暴击率为 5%，暴击伤害为原伤害的 150%，在原始伤害计算的最后阶段结算。
- 一次命中可包含多个独立伤害段，每段按规则处理护甲。命中触发与伤害后处理区分，追加伤害不会自动产生新的命中。
- 描述为“追加一次伤害”时分别计算；描述为“攻击命中时提高 20 点物理伤害”时并入本次命中的物理伤害。没有通用的造成伤害时触发入口。
- 普通状态保留状态整体等级；状态效果包含来源、层实例、持续时间和快照数据，层实例不带等级，默认各层独立计时，各施加者独立生效。整体等级与叠加层数分开，具体等级成长/缩放在相应内容实施前确认。唯一、冲突和覆盖通过状态定义表达。
- 普通限时状态默认按冒险逻辑时间计时，在地图及层间准备也计时。房间全员倒地仍暂停战斗模拟，不能将房间战斗时间作为普通状态的默认时间基准。
- 战斗完成、离开房间后，普通状态默认保留并携带剩余时间；特殊状态可声明离场清除。倒地惩罚、诅咒等遵守各自生命周期。
- 装备常驻加成在卸下时移除；装备已经施加的限时状态默认继续至到期，特殊状态可声明绑定装备存在。
- 装备或状态导致最大生命变化时，当前生命保持原有比例。这是此前已确认的规则；明确的治疗、救援及复活操作依各自规则处理。
- 唯一状态在施加阶段拒绝第二个玩家的施加。状态来源精确到玩家的同一技能或物品实例，满层施加刷新最高层持续时间；层实例不带等级。
- 护盾是没有等级的特殊状态，具有持续时间；多来源叠加，同来源覆盖，优先消耗最新施加的护盾，不自然恢复。
- 生命偷取仅作用于攻击，并且极少提供；回复效果通常使用带加成的固定值。

这些是已确认的玩法约束；当前实现见[实装记录](approved-systems.md)，验证范围见[核对清单](implementation-audit.md)。旧阶段计划保留实施历史，不作为当前待完成清单。

## 局外进度与检查点

- 局外成长、仓库和本地身份保存在玩家本地；以后可关联平台账号。
- 房间可按属性、初始货币、初始装备、行动力和特殊节点等类别限制局外加成；内容解锁单独设置，这些规则整局固定。
- 原有个人加成独立应用，行动力和特殊节点团队加成按最高成员应用，再遵守本局允许的范围。
- 完整通关后按已确认规则结算装备入库和局外收益；主 Roguelike 冒险不能从局外仓库带入装备。
- 同一玩家对同一次冒险仅结算一次。种子与开始时间参与冒险标识生成，存档复制及结算去重的具体实现暂不展开。
- 检查点在层间准备完成、进入下一层前保存，不保存完整战斗运行时；异常恢复以检查点为基础。
- 管理员负责选择、恢复和导出检查点。恢复不要求固定原班成员；旧成员恢复原角色要在本层开始前完成，错过后仍可在后续层间准备回归。
- 恢复必须使用原模组版本、加载顺序和分发包 SHA-256。

## 内容扩展与分发

- 模组包采用标准 ZIP 容器，自定义扩展名及包清单；扩展名尚未命名。
- 包可包含 Go 源码、JS、标准 JSON 和资源文件。JSON 使用下划线开头的字段承载注释信息。
- Go 模组在两端编译，通过公共、服务端、客户端入口区分执行。玩家手动触发构建，开发包附 SDK/宿主源码；缺少 Go 时下载并校验锁定工具链。
- 本体预编译，模组单独编译后重新静态链接；首版只支持纯 Go 依赖。
- 作者推荐声明兼容范围，组合构建锁定精确版本；优先复用既有锁定版本，没有共同可用版本则阻止构建。
- 支持多套组合及同一模组多个已安装版本。依赖优先于自由加载顺序；内容使用模组命名空间，覆盖采用显式声明。
- 所有校验统一使用 SHA-256，分发包身份按整个 ZIP 的字节摘要确定。
- 含 Go 的包不能热重载；仅外部数据或资源改变时可重启复用程序。其他包支持单局外重载，整局进行期间禁止重载。
- 构建或组合加载失败保留上一套可用组合。
- 必需玩法包及资源遵循服务器清单，可从服务器下载；个人界面和外观可独立使用。
- 材质包仅含资源和 JSON，可以替换原版及其他模组的图像、字体、界面、音效和音乐，只改变安装者看到的表现。
- 普通局外成长可按规则应用于玩法模组或特殊模式，所获进度不能直接回流正常模式；按玩法组合隔离保存。

## 固定格位、堆叠与 Hover（2026-10-08）

- 背包不自动排序或补位。左键拿起整堆，再点击放下/合并/交换；右键拿起半堆（奇数向上取整，最少 1），手持时右键放下 1。
- 武器、防具、饰品不堆叠；当前只有消耗品可堆叠，每堆上限 30。JSON 的 `stack_limit` 可将消耗品上限设为 1–30；装备最多为 1。省略时消耗品为 30，其余为 1。
- 合并要求定义以及所有已有实例数据（修饰、强化等级、强化数值）完全相同。后续新增组件必须一起补充兼容判定、复制与校验；当前不额外发明 NBT 字段或新的物品规则。
- 手持物品由服务端鼠标槽持有，仍属于玩家。关闭背包或断线时按拾取规则回收：先并入兼容背包堆，再使用空格。已有格位不重排。事务预留回收容量，避免手持期间奖励占满空间后无法回收。
- Hover 继续跟随鼠标只读，只通过 Shift 展开信息。统一标题/正文间距与语义颜色，简明描述不混入无关武器公式；普通窗口的交互规则不变。
