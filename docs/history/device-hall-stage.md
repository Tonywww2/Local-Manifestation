# 统一装置、主菜单与个人大厅

> 历史交付记录。后续 Hover 已改为不可拖动的鼠标只读提示，与普通窗口分离；本轮测试改为仅编译及少量必要实机检查。当前规则、修复和未完成范围见[核对清单](../implementation-audit.md)。

日期：2026-10-08。本批原版包 **0.5.0**、网络协议 **9**、SDK **5**、检查点 **5**；JSON 内容格式仍为 **2**。同时更新客户端、服务器和内容，并开始新冒险。客户端偏好格式仍为 1，已有语言、键位和 HUD 布局保留。

## 装置结构

`pkg/device.Device` 是所有世界交互共用的纯值基础类型，保存稳定身份、显示名称/描述与本地化键、世界位置、交互范围、拾取半径、动作和目标。`Entrance` 嵌入 `Device`，增加房间入口的类型、付款方式和费用；Go 用组合表达用户要求的基础类型与房间入口子类型，不建立没有调用者的继承框架。

战斗、BOSS、事件和通路入口共用房间入口构造函数。房间清理或开门不会改变入口所属类型。商店、下一层出口、强化 BOSS/耗尽投票与个人大厅设施使用同一基础装置。`device.World` 从权威节点、场地、阶段等显式输入派生装置；装置并不自行扣行动力、执行脚本或写玩家状态。

客户端绘制、双视角拾取、接近提示和服务端距离校验使用同一位置与范围。UI 点击及 G 交互进入统一动作适配，再调用原有的确认、团队投票、商店或大厅事务。付费入口仍需确认，共享入口仍通过实体装置投票，免费通路仍连续走过；抽象装置不改变这些已确认规则。

商店现在具有实际场景装置及可拖动的强化窗口。即使直接发送旧的 `upgrade` 请求，服务端也要求玩家在商店装置范围内；拒绝远程操作不扣货币、不改强化。当前只提供已有 JS 锻造商店的武器强化，正式商品目录、出售、物品实例和交易仍在后续阶段。

JSON 节点仍通过 `name/name_key` 和 `hint/hint_key` 定义入口显示信息，商店动作仍通过注册节点处理器执行。基础装置结构是引擎代码契约；本批没有声称已提供任意新装置的 JSON 注册器、资源包美术或完整模组分发加载器。

## 显示与输入

- 场景装置默认只绘制图形与图标。鼠标悬浮显示名称，按住 Shift 后显示一句简介；复用可拖动、可固定的 Hover。
- 世界拾取框由同一个相机投影生成，俯视与斜俯视共用世界点。只有可见部分参与拾取，HUD 与浮窗优先，点击不会穿透成装置交互或开火。
- 交互仍需走近装置。近距离 HUD 提示使用当前 G 绑定；自定义键位立即反映在提示中。点击远处装置不会执行其动作。
- 已有具体状态左键不打开额外页面，状态 Hover/Shift 行为保留。

## 主菜单与个人大厅

主菜单默认只有“开始游戏、设置、退出”。开始游戏打开本机个人大厅，不直接连接或开局；设置复用原生设置窗口，退出结束客户端。标题暂使用工程名 HSMultiplayer。

个人大厅是本地可走动的六边形场景，具有角色和六种装置。它尚未运行冒险时钟，不授予局内奖励；进入真实冒险后，生命、行动力、战斗和状态仍由独立服务器裁定。

| 装置 | 本批实际行为 |
| --- | --- |
| 单人冒险 | 启动仅监听本机的独立服务器，临时限制一名玩家，连接成功后自动开始首层；不改掉保存的多人配置 |
| 房间配置 | 草稿调整人数、通过比例、30/60 TPS、快照频率、端口、昵称和初始机体；保存后替换偏好文件，取消不提交 |
| 创建联机大厅 | 按保存配置启动独立服务器，监听联机地址，进入准备大厅；管理员决定何时开局 |
| 加入服务器 | 可拖动的地址/昵称表单；保留原有个人身份和重连路径，Tab 切换字段，Enter 连接 |
| 局外成长 | 装置及窗口已建立，明确说明成长树、点数和学习事务尚未接入；不虚构加成或收费规则 |
| 仓库 | 装置及窗口已建立，明确说明物品实例、带出结算与存储尚未接入；不伪造库存或物品操作 |

人数默认上限 8，可保存 1–128；共享投票默认 70%，逻辑默认 30 TPS、快照默认 20 Hz。大于 8 的配置不代表已完成高人数性能验收。配置在服务器启动时应用，运行中不通过客户端设置修改权威规则。

启动独立服务器在后台执行，先等待其真正监听成功再连接。端口占用或启动失败不会误连另一台本机服务器，也不删除旧重连身份。创建新冒险的 Hello 使用新身份，welcome 成功后才保存新 token。返回个人大厅断开连接；房主启动的服务器随客户端退出或返回大厅结束，独立启动的外部服务器不受影响。启动期间不重复提交创建动作。

## 继续既定 S3：倒地记录与惩罚

`pkg/life` 是纯值生命转换核心。玩家新增 `knockdowns` 倒地事件记录，原 `downs` 字段明确表示当前可移除的惩罚层数。生命归零时仅记录一次事件；普通救援增加一层惩罚，减少惩罚不删除记录，第四次倒地进入死亡。普通救援不能复活死亡角色。

普通难度惩罚仍按 `1 − 0.25 × 当前惩罚层数` 线性作用于最终生命上限与最终攻击伤害。两者共用因子和稳定来源 `engine:down_penalty`，保留已有计算顺序。更改最大生命仍保持比例；实际救援恢复满生命，层间恢复减少一层惩罚并恢复满生命，且保留事件记录。属性或状态刷新不会让倒地角色自动站起。

场景所有者记录生命转换，协调器只在战斗外救援。多人救援先计算所有候选，再一次提交，失败不产生部分救援。检查点验证生命身份、事件记录、惩罚及派生属性；同一玩家的记录通过场景、重连和层间值交接保留。状态/本人 Hover 显示事件记录与惩罚，二者不混为一个计数。

特殊难度、死亡复活设施及其关联的后续记录规则仍在对应内容实施前落实；本批没有新增这些内容或数值。

## 验证与下一项

测试覆盖基础装置与入口类型、可达大厅设施、双视角拾取、浮窗遮挡、默认名称/Shift 简介、远程拒绝、配置草稿/保存/重启、启动失败保留身份、独立时间步移动、线性惩罚、第四次倒地、救援事务和检查点记录校验。

原生 Windows 验证覆盖中英文、1024×720 / 1280×800 / 1920×1080、双视角、主菜单/设置/大厅/Hover/加入/配置/仓库窗口。真实单人装置启动私有服务器并产生检查点；两个原生客户端通过创建和加入装置连接，验证保存的 60 TPS / 10 Hz 配置、人数上限拒绝第三人及身份重连。

同时复核游戏内商店窗口及付费入口 Shift 简介。双原生客户端使用明确的开发压力内容同时在两个战斗房间运行，在 120 FPS 上限、VSync 关闭、60 TPS / 60 Hz 输入下，测得约 **114.86 / 114.86 FPS**，场景与输入均为 **60.00**。这仅是当前占位内容的回归基线，不是高人数容量保证。全量测试、相关竞态检测、静态检查及 Windows/Linux 构建通过。
