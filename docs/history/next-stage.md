## 前置工作：逻辑刻与渲染帧独立

### 改造前低帧感的来源

| 层次 | 改造前代码 | 改造前频率/行为 |
| --- | --- | --- |
| 服务端战斗模拟 | `internal/scene/scene.go` 的 `tickRate` 和 `Actor.run` | 固定目标 30 TPS，单场景独立 goroutine；`step(1/30)` |
| 服务端快照发布 | `internal/session/session.go` 的协调器定时器 | 50 ms 一次，即目标 20 次/秒 |
| 客户端输入与消息处理 | `internal/client/game.go` 的 `Update` | 使用引擎默认 60 TPS；常规输入每两个 Update 发送一次，目标约 30 次/秒 |
| 客户端绘制 | `cmd/client/main.go`、`Game.Draw` 和 `drawBattle` | 默认 VSync，未配置独立数值帧率上限；直接绘制最新快照位置，无插值 |

30 TPS 是服务端模拟目标，不是客户端 FPS 上限。即便绘制达到 60 FPS，每份 20 Hz 的快照仍会重复显示约三帧，位置每约 50 ms 跳变一次；这是代码能够确认的视觉卡顿原因。改造前没有 FPS/TPS 实测日志，不能将当时的低帧感直接认定为实际绘制只能达到 20 FPS。

改造前逻辑定时器直接接收 `time.Ticker` 并执行一个固定步长，没有积累时间与补刻策略。现在采用固定步长累积器和实际频率计量，负载高时不会以配置目标代替实测结果。

### 已确认目标与实施边界

| 频率 | 负责的内容 | 要求 |
| --- | --- | --- |
| 服务端逻辑 TPS | 世界移动、碰撞、伤害、冷却、状态及逻辑时间 | 固定 30 或 60 次/秒；不随客户端 FPS、显示器刷新率或网络快照频率改变 |
| 网络快照频率 | 发送已裁定状态 | 独立配置；无需为了高 FPS 每帧发送全世界 |
| 客户端渲染 FPS | 世界显示、投影及视觉动画 | 使用独立帧率上限；VSync 单独设置，实际频率还受设备与显示同步限制 |
| 输入采样与发送 | 操作意图、一次性操作和消息处理 | 不以渲染帧数取模决定发送；保持明确的处理/发送节奏 |

服务端继续独立运行，按固定步长模拟并发布带逻辑刻、频率及时间信息的只读快照。补刻使用积累时间和有界预算，实际跟不上目标时记录指标，不能通过改变每步 `dt` 隐式改变玩法速度。

客户端保存短期快照历史，在每个渲染时刻对位置插值，人物、敌人和投射物按同一显示时间轴绘制。默认缓冲 100 ms，可配置为 0..2000 ms；显示缓冲会增加延迟。本机玩家普通移动显示预测与校正已接入，仍不代替权威碰撞；见跨房记录。

插值不重新裁定碰撞、伤害或状态；同场景、同实体身份才能插值。切换房间、重连、暂停、传送以及实体生成/消失时处理历史边界，不能跨不相关位置拉出移动轨迹。俯视与斜俯视对同一显示位置投影，鼠标意图仍提交世界坐标。

Ebitengine 的 `Update` 和 `Draw` 本来就可以使用不同频率，但仍在同一 goroutine 回调；服务端模拟与客户端绘制已通过独立进程分开。引擎提供固定 TPS 及 VSync 开关，当前公开接口没有直接设置任意数值 FPS 上限的入口。帧率上限需要独立绘制调度，不能用 `SetTPS` 代替，也不能仅重复旧画面却将引擎回调次数称为目标 FPS。参见 [Game 与 RunGame API](https://pkg.go.dev/github.com/hajimehoshi/ebiten/v2#Game) 和 [SetTPS](https://pkg.go.dev/github.com/hajimehoshi/ebiten/v2#SetTPS)。

前置验收应分别显示/记录实际渲染 FPS、服务端 TPS、输入发送与快照接收频率，并在不同渲染上限下验证移动速度、攻击间隔和相同逻辑刻数的结果一致。固定逻辑 30/60 TPS、渲染上限高于及低于逻辑频率两种情况都要覆盖；高渲染频率下显示位置应在快照之间变化，切房/暂停边界不残留旧场景插值。

## 实现后的可验证结果

玩家能查看并装备一把武器、四个部位的护甲和饰品，背包保存具有独立身份的物品；服务端验证每次操作。装备与状态共同影响派生属性，卸下或状态到期后重新求值，不通过反向减法恢复基础属性。

普通状态保留状态整体等级，与层数分开；状态具有施加者、具体技能/物品来源、独立层实例、快照和剩余时间，层实例不带等级。整体等级的成长/效果缩放在对应内容实施前确定。护盾仍无等级，复用状态生命周期，支持多来源、同来源覆盖和最新优先消耗。玩家在地图、不同战斗房间及层间交接时，实例身份与状态数据保持一致。

同一次求值提供真实结算和伤害解释。解释能展开每个乘区中的具体装备、属性和状态贡献；一次命中包含多种伤害时，每个伤害段独立计算护甲，并记录护盾吸收和实际生命损失。

验证继续覆盖单人开局、多人分头战斗、中英文、双视角、救援与层间检查点。首版仍使用占位内容，完整随机地图、主动技能库、经济平衡、局外仓库和公网发布在各自阶段实施。

### 定义、实例与派生结果

定义 ID 表达“某一种内容”，实例 ID 表达“本局的这件物品或这层状态”。同名武器放入背包后仍是不同实例；装备栏引用实例 ID，出售、强化、交换都针对实例，不能用背包下标作为身份。

属性保留机体基础值、等级分配和各来源贡献。装备或状态变化使派生结果失效，由统一入口重算。现有机体生命、护甲和移速继续作为基础值；六种属性是否额外换算生命、移速等，在相关设计落实前不增加隐含规则。

来源分别记录施加者 ID、技能或物品实例 ID、内容定义 ID 及施加次序。同来源精确到施加玩家及其同一个技能或物品实例，这些身份不能压缩成一个显示字符串。物品转移后，已施加状态的施加者身份也不能随新持有者改变。

乘区保留稳定的组 ID 和各项贡献。计算使用组 ID，同组加算、不同组相乘；显示名称和来源名称使用本地化词条。解释逐项展示贡献，避免只能看到拼接后的“装备 + 状态”字符串。

### 状态与护盾

普通状态独立保存层实例、剩余时间和施加时求得的快照，不再增加层实例的等级字段。施加后不重新读取施加者当前属性来改变已有效果。默认各层独立计时；特殊状态的计时、替换、冲突和层数规则必须在定义中明确表达。

普通限时状态默认使用冒险逻辑时间，在地图和层间准备也计时。完成战斗、离开房间时保留未到期状态及剩余时间；特殊状态可声明离场清除。倒地惩罚、诅咒等继续遵守明确的独立生命周期。

装备常驻贡献随卸下移除；已经施加的限时状态默认继续至到期，不因卸下来源装备而清除。需要随装备消失的特殊状态必须显式绑定装备存在；保留的状态仍使用原快照和来源身份。

唯一状态在施加阶段检查并拒绝第二个施加者；失败不能先删除旧状态或提交部分属性变化。达到层数上限再次施加时刷新最高层的持续时间，特殊逻辑走注册扩展入口。

同一套状态生命周期支持玩家与敌人，但不要求敌人也具有六种玩家基础属性。控制类状态保留效果贡献和抗性校验入口，具体眩晕、减速等内容在实现相应敌人或技能时讨论。

护盾是没有等级的特殊状态，保存剩余吸收量、来源、持续时间和施加次序。多来源并存，同来源覆盖；消耗按最新施加次序进行，不能依赖 slice 或 map 的偶然顺序。离开房间后，次序仍须可比较。护盾没有自然恢复，到期后移除剩余护盾。

倒地惩罚复用属性贡献和解释，但救援、死亡及复活仍由宿主生命状态机裁定。团队诅咒继续属于冒险规则，其行动力影响在下一层初始化时计算，不能被清除普通玩家状态的操作意外解除。

### 伤害链与内容触发

保留普通加算 → 命名乘区 → 最终加算 → 暴击 → 已定义最终修正的攻击求值顺序。之后按每段处理护甲、抗性和分别相乘的百分比减伤；免疫及最低伤害沿用已确认规则。两位小数仍在最终结算边界处理，中间过程不提前舍入。

“命中时提高 20 点物理伤害”作为本次命中的规则贡献，合并进该命中的物理段；“追加一次伤害”建立独立段。每段计算一次护甲。默认暴击率 5%、暴击伤害 150%；多段暴击等尚需核对的边界，在实现伤害段前读取已有记录，不能从缺失上下文的字母答案猜测。

命中规则贡献必须在当前伤害求值前收集，返回经过验证的值。现有事实事件监听在事件发生后提交命令，不能用它事后改写已经计算的伤害。引擎提供独立的贡献接口，并对 Go 和 JS 应用相同的来源、执行预算和验证规则。

一个实际命中只触发一次命中事件。后续伤害段、周期伤害或追加伤害不能自动递归产生新命中。`after_damage` 记录已完成的结算，保留当前实际生命损失的语义，另外提供护盾吸收等结果；没有通用的“造成伤害时”触发入口。

护盾消费接在防御计算之后、生命扣除之前。结果分别记录防御后的伤害、护盾吸收、实际生命损失与过量伤害，使护盾完全吸收时生命损失可以为 0。生命偷取只允许来自攻击；普通固定值恢复沿用内容的加成规则，不自动变成偷取。

### 装备、背包与成长

装备栏包含一个武器位置、头部/身体/腿部/脚部护甲位置和饰品位置。普通模式使用有限饰品槽及有限背包；游戏开始前的特殊设置可调整容量，饰品支持无上限的动态扩容。无上限作为显式配置表达，不用巨大整数伪装上限。

物品实例保存定义引用、强化进度与修饰数据。现有 `Upgrade`、`WeaponBonus` 迁入所持武器实例，避免切换武器后强化错误地影响全部武器。饰品修饰与基础定义分开，乘区组仍按具体内容定义归属，不把所有强化饰品合并为一种新乘区。

装备操作先验证实例归属、槽位、容量、内容限制及当前阶段，再提交完整变更。属性刷新和生命上限变化在同一事务中完成。背包满、过期请求或非法限制不得造成物品消失、复制或部分装备成功。

装备或状态改变最大生命时保持当前生命比例：`新生命 = 旧生命 / 旧最大生命 × 新最大生命`，按最终生命边界处理精度。例如 50/100 改为最大生命 200 后为 100/200。此规则此前已确认，本次仅补齐记录；明确的治疗、救援和复活仍执行各自规则，上限变化本身不能改变倒地或死亡身份。

先接入现有机体初始武器、商店强化和恢复节点，增加足够验证流程的占位物品及状态。装备数值、饰品数量、稀有度、掉落和出售价格仍待相应内容实现前讨论。

物品交换已纳入本批，采用双方确认、实例归属检查和一次完整提交；重复提交、断线或物品变化不能重复转移。不得直接交换货币。交换的可用位置及战斗限制在该模块实施前确认。

## 时间、并发、同步与恢复

战斗房间仍独占其中玩家与敌人的可变战斗状态，冒险协调器处理场景外玩家。玩家交接传递完整的纯数据副本；不同房间不共享可变背包、状态层列表、修饰参数或属性贡献集合。

当前 `Player` 已包含属性贡献列表，属性基础阶段已在场景交接、快照、SDK 上下文及显示副本中使用嵌套复制。加入状态、物品及修饰数据时继续审查所有边界：场景入场与合并、快照、网络编码、SDK 上下文、命令预提交副本及检查点。复制后不得再由异步编码器读取正在修改的原始数据。测试必须实际修改嵌套内容来证明隔离。

时间由宿主推进，不使用电脑墙钟计算持续时间。冒险协调器提供统一冒险逻辑时间，普通状态按该时间域计时，地图和层间准备也推进时间。全房倒地仍停止该房间的战斗模拟及战斗逻辑时间，不将普通状态切换为战斗计时；波次间仍属于战斗中。

状态由实体当前所有者结算，保存剩余时间、时间域及必要的已结算时间记录。离场默认保留状态和剩余时间；交接不能重复推进或遗漏冒险时间，也不能让暂停的房间暂停整局冒险时间。装备卸下仅移除常驻贡献和显式绑定装备存在的状态。

状态到期、装备变更及属性贡献变化统一标记派生结果失效，避免每帧扫描全部装备并重算所有属性。先测量多状态、多物品和 8 个独立场景的开销，再决定是否引入专用到期调度结构，不预先承诺复杂优化。

网络发送服务端认可的实例和展示结果；客户端不能自行提交最终属性、护盾余额或物品数据。操作携带实例身份及版本等校验信息，服务端拒绝重复或过期变更。客户端预览明确目标防御和条件假设，不替代真实结算。

层间检查点保存物品、装备引用、状态快照和所需的剩余时间/次序等纯值，恢复时先检查所有引用和限制，再重建贡献及处理器。仍不保存 VM、函数或完整战斗运行时。跨层状态的保留或清除需要显式生命周期规则，不能因为进入新房间就默认全部清空。

内容格式、SDK、协议和检查点版本分别审查，在对应实现完成时更新。2A-0 只提升网络协议至 4；属性基础已提升协议至 5、SDK/检查点至 3；后续状态与物品实例再独立审查版本。旧开发检查点若无法表达新实例，不通过忽略摘要或猜测实例进行兼容，先给出明确错误。

每个步骤先通过针对实际行为的检查，再进入依赖步骤。需要保留的一组核心验证如下：

- [x] 多来源状态并存，唯一状态的第二个施加者被拒绝，拒绝不会破坏旧状态。
- [x] 每层独立到期；暂停、离场、跨房交接及刷新按确认的时间规则执行。
- [x] 普通状态在地图及层间准备继续按冒险时间计时；暂停房间不推进战斗模拟，交接不重复扣时间。
- [ ] 施加者属性变化后，既有状态快照不变；装备变更能正确刷新当前派生属性。
- [ ] 卸下装备移除常驻贡献，默认保留已施加的限时状态；显式绑定装备存在的状态随卸下移除。
- [x] 最大生命上升或下降均保持当前生命比例；不改变倒地/死亡身份，明确的治疗与救援仍按各自规则执行。
- [ ] 护盾同源覆盖、多源叠加、最新优先和到期正确；免疫不消耗护盾，吸收量不为负。
- [ ] 多伤害段独立计算护甲，附加物理贡献正确合并；一命中不会因多段而重复触发。
- [ ] 伤害解释、预览和实际结算共用求值数据，能定位到具体状态或物品实例贡献。
- [ ] 切换、强化、卸下与容量拒绝都保持实例一致；不同房间的嵌套数据互不影响。
- [ ] 救援/复活/清惩罚不意外恢复护盾或物品，倒地事件记录与惩罚分离，第四次倒地进入死亡状态。
- [ ] 临时重连和层间恢复得到相同实例与派生结果，不重新抽修饰或重复奖励。
- [ ] 交换时重复确认、容量不足和断线不造成部分成交。
