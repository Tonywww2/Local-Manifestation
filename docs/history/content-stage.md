# 第一批实现记录：内容定义与注册接口

第一批内容定义与注册接口已实现，地图、节点、房间和波次使用可校验的 JSON 定义。后续再接入正式状态及装备系统。第一批交付以现有三层开发流程为迁移基准：内容作者可以调整或增加房间模板，而行动力、团队投票、救援和 BOSS 集结仍由 Go 服务端裁定。

本文件保留第一批的迁移方案及完成清单，下表是迁移前基准，不代表当前代码。实际格式、接口、运行命令和性能数据见[内容定义与 SDK](../content.md)。当前待实施的状态与装备方案见[下一阶段实现方案](next-stage.md)。

本方案规定工程顺序和模块边界。测试配置中的数量、收益、价格和强化比例仍是占位值；新增玩法与平衡规则在对应模块实施前讨论。已确认规则见[设计记录](../design.md)，完整目标见[基础架构方案](../architecture.md)。

## 第一批实现 内容驱动的节点与战斗

这一批完成后，修改原版 JSON 应能改变房间敌人、波次组织、等待时间和占位收益，无需修改 Go 模拟代码。增加一个使用已有行为的新房间模板，也不应要求增加节点种类判断。

### 定义与实例

共享的纯数据类型继续放在 `pkg/model`，按职责拆分文件。拟增加以下类型；字段在这一批实现时与加载器、协议和 SDK 一起落实。

| 类型 | 负责的数据 | 不应保存的数据 |
| --- | --- | --- |
| 层定义 `FloorDef` | 初始个人与共享行动力、地图模板引用、普通与强化 BOSS 房间引用 | 玩家余额、已开门记录 |
| 地图模板 `MapTemplateDef` | 六边形位置、实际连接边、节点定义引用 | 本局完成状态 |
| 节点定义 `NodeDef` | 类型、提示词条、付款方式、房间或处理器引用、入场策略 | 投票、实际参与成员 |
| 房间模板 `RoomDef` | 场地、目标处理器、波次、出生规则、缩放与奖励配置 | 敌人当前生命、倒计时 |
| 波次定义 `WaveDef` | 敌人 ID、数量与位置配置、波次衔接、奖励引用 | 本次已击杀敌人 |
| 节点访问与战斗实例 | 定义 ID、节点实例 ID、实际参与、消费、进度、结算记录 | JS 函数、虚拟机和 Go 指针 |

定义的内容 ID 使用包命名空间；地图上的节点 ID 和战斗实例 ID 表达本局位置与访问。房间引用敌人 ID，消除“第一个敌人是小怪、最后一个敌人是 BOSS”的数组顺序依赖。现有普通和强化 BOSS 通过同一场景创建入口加载各自配置。

第一步先将固定地图转为模板。之后再实现按人数及进程生成地图、房间模板尽量不重复等既定方向，生成器不得改写已经开始的层。这样可以分别验证模板执行和随机生成，避免同时改变地图与战斗规则。

### 服务端职责

`internal/session` 保留可达性、开门、行动力、成员资格、投票、BOSS 集结、层推进和检查点事务。内容处理器只能请求操作或返回待验证的结果，不能直接设置团队余额、其他玩家所属场景或全局完成状态。

`internal/scene` 接收已解析的房间配置，继续独占战斗世界。场景负责实体、移动、碰撞、波次执行和战斗事件；不同场景的内容运行时各自隔离。内容配置不得让一个场景直接写入另一个场景的状态。

随机流按冒险种子、层和节点实例身份派生，避免使用活动场景数量作为内容随机身份。生成结果由服务端保存和同步；客户端只展示本次实例，不重新生成地图。

### 内容加载与注册

加载流程分为读取、解析、定义索引、引用校验、脚本编译、注册验证和可用目录发布。任何一步失败都不发布半成品目录，错误至少指出文件、定义 ID、字段或缺失引用。

目录发布后冻结。共享目录保存 Go 值、只读索引和已编译程序；JS 函数、监听器和执行状态属于各运行上下文。关闭场景时清理其监听器和命令队列，防止下一场景继续收到旧内容回调。

内容查询接口避免返回可被调用者修改的内部 map 或 slice。新定义文件同时更新原版嵌入清单；内嵌、外部和归档加载使用同一套校验路径，防止发布程序漏带模板。

这一批继续使用单包加载路径，保留以后按依赖和显式覆盖构建组合目录的边界。加载性能分别记录读取与校验、解析、脚本编译、运行时注册；先取得基线，再决定缓存位置和容量。

热重载的发布入口只允许在单局之外使用，层间准备仍属于单局之内。目录冻结和发布边界在本批建立；模组管理界面、文件监听、多包下载和组合切换在后续扩展阶段接入。

### SDK 与事件契约

SDK 保持不依赖 `internal`、Ebitengine 和 goja。Go 与 JS 内容使用同一套值类型与宿主校验，通过适配器完成注册和调用。

注册阶段建立定义与行为关联，并检查重复 ID、未知处理器和不匹配参数。运行阶段通过限定上下文查询快照、监听事实事件和提交值命令。上下文带所属冒险或场景身份，宿主验证目标、资源、权限和执行阶段后才修改状态。

保留 `hit` 和 `after_damage` 的不同语义：命中效果使用命中入口，恢复等伤害后处理读取结算结果；追加伤害不自动创造一次新命中。正式事件数据需要区分攻击、命中和伤害段身份，并区分实体实例与内容定义，避免多伤害段重复触发。

规则贡献使用专门的求值接口提供属性、乘区或防御数据。事实事件发布后的命令进入所属上下文的受控队列，不允许监听器取得可变世界指针，也不依赖监听先后顺序悄悄修改当前公式。监听执行顺序、退订时点、递归限制和脚本执行预算作为 SDK 行为契约测试。

这一批先开放迁移现有内容所需的最小接口。完整技能、状态和物品行为随各模块增加，避免提前承诺无法验证的公共 API。

## 第一批工作顺序

| 顺序 | 实现范围 | 可审阅产物与验收 |
| --- | --- | --- |
| 1 | 共享定义、版本与校验 | 纯值类型、JSON 字段说明、引用检查；未知字段、重复 ID、未知敌人和非法参数拒绝加载 |
| 2 | 原版模板迁移 | 将现有地图、房间、刷怪和波次参数写入 JSON；原版配置仍能完成既有三层流程 |
| 3 | 场景创建与波次执行 | 场景按房间配置运行；不同模板、不同尺寸和不同敌人列表不依赖定义数组顺序 |
| 4 | 节点处理器与事务接入 | 原版商店和恢复节点走注册入口；失败入场不扣费，共享开门仍只付费一次 |
| 5 | 事件与脚本接入 | JS 示例可监听事件并提交合法动作；非法跨场景操作拒绝执行，脚本错误有来源诊断 |
| 6 | 联机、恢复与分发 | 单人、双人分场景、BOSS、救援、恢复和中英文显示回归通过；更新 Windows 开发包及内容说明 |

每一步使用已有占位数值迁移。需要扩充格式或公共接口时，分别审查内容格式、SDK、协议及检查点版本；它们不能相互替代。内容摘要不一致仍拒绝连接或恢复，不通过忽略摘要来兼容旧开发存档。

## 后续依赖（第一批规划时的记录）

内容驱动的流程稳定后，先实现正式状态和派生属性，再实现装备、背包及成长。这能让饰品、护甲、主动技能、护盾和倒地惩罚复用同一套属性贡献及生命周期。

| 模块 | 已确认约束 | 实现前需要落实的接口 |
| --- | --- | --- |
| 派生属性 | 六种基础属性、带来源的加算与乘区、伤害解释复用 | 基础值、装备贡献、状态贡献、临时结果及重新计算边界 |
| 状态 | 施加者独立、各层独立计时、快照计算；唯一状态在施加时拒绝另一来源 | 状态定义、每层实例、来源身份、冲突检查、替换与到期生命周期 |
| 护盾 | 特殊状态、无等级、多来源叠加、同来源覆盖、最新优先消耗、不自然恢复 | 吸收顺序、实际生命扣除、伤害后结果和同步数据 |
| 装备与背包 | 一把同时使用的武器、多把可存储、头身腿脚护甲、饰品槽及背包容量可配置 | 装备实例 ID、槽位、修饰、交换事务和服务端更新 |
| 技能及消耗品 | 沿用已有输入方案，通过内容形成玩法倾向 | 输入意图、目标快照、费用、冷却、内容命令和表现事件 |

具体状态时间基准、刷新目标等规则在正式状态模块前与已确认记录核对，确有未定的边界再集中讨论。装备数值、初始技能、敌人机制、掉落表和经济平衡在相应内容实现前讨论。

倒地惩罚、强化和敌人成长目前仍有写在代码中的测试公式。迁移时为它们保留来源和规则边界；正式数值模块按已确认规则复核，不把这些公式自动作为最终平衡。
